Abstract

Ask a documentation assistant how many chips are in one Cloud TPU host or VM and the right answer depends on the generation: 4 for v5p, 8 for v6e, 4 for TPU7x234. Ask which software version to pass when creating a TPU7x VM and the right answer is that the Cloud TPU API doesn't support TPU7x at all5. Retrieval ranks text by meaning, not by generation, so it returns all of these side by side. In a published benchmark, standard RAG answered only 58% of version-sensitive questions correctly6.

VALID (Version-Aware Lookup In DITA) is an agent that answers only from content profiled for the reader's generation. The scope of every chunk comes from what writers already maintain: profiling attributes, map cascading and a subject scheme810. Firestore filters on scope before the vector search runs12. Gemini writes the answer, and plain Python checks that every citation is in scope and every value appears in its source. If no in-scope content exists, VALID says so and opens a gap issue. It never widens the search to another generation.

VALID is rebuilt from VaultRAG, a deployed RAG service with guardrails that refuse when unsure25. It keeps that service's retrieval stack and refusal design, and replaces plain-text chunking with DITA-aware chunking that carries scope.

§1 Client Brief

The client is Google's data center products and services documentation. The sample content is the Cloud TPU documentation for three hardware generations: TPU v5p, TPU v6e (Trillium) and TPU7x (Ironwood)234, plus the TPU software versions page that covers all of them5. The MANIFEST project converted this content to DITA, with generation-specific content marked by profiling attributes and built per generation with DITAVAL27.

It is a good test for two reasons. First, the generations share most of their concepts and procedures, so retrieval can't tell them apart by meaning alone. Second, the differences are small, exact and easy to get wrong: a chip count, a version string, a supported API. An answer that is almost right is a wrong answer here.

§2 Problem Statement

A documentation assistant is only worth its cost if readers trust its answers enough not to ask a person. Hardware generations make that hard. Most of the text is shared, the differences are small, and a retriever can't see which generation a sentence belongs to.

2.1 One question, three right answers

A real example
The TPU software versions page lists one version string per generation for JAX and PyTorch: v2-alpha-tpuv5 for v5p and v2-alpha-tpuv6e for v6e. On the same page, it says the Cloud TPU API is not supported on TPU7x and later, and points to Compute Engine or GKE instead5. A reader who asks "which version do I use for my Ironwood VM?" is closest in meaning to the version table. A retriever returns the table. A model then does what it was asked and picks a version string.

2.2 How often RAG gets it wrong, and what it costs

The VersionRAG study measured this failure on versioned technical documentation: Apache Spark and Bootstrap release notes, and Node.js reference pages, 34 documents and 100 curated questions6. Standard RAG answered 58% correctly. On questions about what changed between versions, it answered 25% correctly (Figure 4).

Figure 4
Accuracy on version-sensitive questions, by retrieval approach
standard (naive) RAGGraphRAGVersionRAG, version-aware
Data from Huwiler, Stockinger and Fürst, VersionRAG, Table 5, with DeepSeek-R1 70B as the model6. Different content from this design, the same failure. The version-aware approach built its index with about 97% fewer tokens than GraphRAG6. VALID goes one step further: in DITA, the version structure already exists, so it needs no model to build it.

The cost of an almost-right answer is not the answer. It is what the reader does next. In the 2025 Stack Overflow Developer Survey, the most common frustration with AI tools was answers that are almost right, but not quite, at 66%. Three in four developers said they still ask a person when they don't trust an AI answer7. Each wrong-generation answer turns a self-service answer back into a question for an engineer.

Figure 5

Stack Overflow 2025 Developer Survey, AI section7. Between 29,163 and 33,244 respondents per question. The survey is about AI tools in general, not documentation assistants. It shows the reader's fallback when an answer can't be trusted.

Problem statement
Readers of the Cloud TPU documentation ask questions whose correct answer depends on the TPU generation. A standard documentation assistant retrieves by meaning, so it returns content from every generation and can answer with a value or procedure from the wrong one. Readers who can't trust the answer ask a person instead, and the assistant saves nothing. The DITA source already records which content applies to which generation, but the assistant never sees it.

§4 User Stories

Each story has acceptance criteria that a tool or check in §5 tests.

US-1 · Documentation lead
As the documentation lead, I want every answer's scope, citations and cost logged, so that I can show the assistant is right before I fund it further.
Accepted when: log_question writes one row per question with the resolved scope, cited chunk IDs, check results, tokens and cost; the trap-set report in §7 reads only that table.
US-2 · Technical writer
As the Cloud TPU writer, I want answers built only from content I profiled for the reader's generation, so that my profiling decides what readers see.
Accepted when: retrieve_in_scope sends an equality pre-filter on scope with every query; check_answer fails any answer that cites a chunk outside the scope.
US-3 · Information architect
As the information architect, I want VALID to take its generations from my subject scheme and report unscoped generation values, so that there is one source of truth for scope.
Accepted when: resolve_profiles fails the index build on any profiling value not in the subject scheme; audit_scope opens one issue per unscoped chunk that contains a generation-specific value.
US-4 · Software engineer
As a Cloud TPU software engineer, I want every command and flag in an answer to appear in an in-scope source, so that no reader runs a command from another generation.
Accepted when: check_answer matches every command, flag and version string, character for character, against the cited chunk text.
US-5 · Support engineer
As a support engineer, I want each answer to name its generation and link only to pages for it, so that I can send it to a customer without checking it again.
Accepted when: the answer schema requires a scope field; every link resolves to a chunk whose scope includes it.
US-6 · Priya, reader
As an ML engineer moving to TPU7x, I want the TPU7x procedure when I say "Ironwood", so that I don't run the v6e command I already know.
Accepted when: resolve_scope maps "Ironwood" to tpu7x from the subject scheme; no v6e or v5p chunk reaches the model.
US-7 · Tomás, reader
As a platform engineer, I want to be asked which generation I mean when my question doesn't say, so that I never get one generation's number presented as the answer.
Accepted when: a question with no scope and a scope-dependent answer returns a choice of generations, not an answer; a question naming two generations gets one cited answer for each.

§5 Proposed Design

VALID v0.1 is an agent built with Agent Development Kit (ADK), Google's open-source agent framework19. It uses Gemini 3.8 Flash (gemini-3.8-flash)15 with structured output, so the answer must match a JSON Schema18, and Gemini Embedding 2 (gemini-embedding-2) for vectors14. Plain Python tools, called through function calling20, do everything else. They decide the scope, run the filtered search and check the answer. The checks decide pass or fail, and the agent can't override them.

VALID has two parts. The index runs on every docs merge: it reads the DITA source, resolves the scope of each chunk and writes it to Firestore. The answer runs on every question: it decides the scope, searches only inside it and checks the result.

5.1 How it works

Figure 7 is the same context as Figure 1, with VALID added. The assistant now reads the DITA source, where the scope still exists, instead of the published pages.

Figure 7

The model sits behind the filter. By the time Gemini sees a chunk, the chunk is already in scope, and by the time a reader sees the answer, every citation has been checked against that scope.

5.2 Scope comes from the source

VALID doesn't ask a model which generation a chunk belongs to. Writers already answered that question when they profiled the content for DITAVAL builds. resolve_profiles reads three things, in this order:

DITA featureWhat VALID readsIndex result
Map cascadingplatform="tpu7x" on a <topicref> applies to every topic under it10The whole TPU7x branch is in scope for TPU7x only
Element profilingplatform on a step, row or section inside a shared topicThat chunk's scope narrows to the listed values
No attributeAn omitted attribute can't evaluate to "exclude", so the content is in every build8In scope for every generation, and checked by audit_scope
Subject schemeThe allowed @platform values and their other names11One field per value; any other value fails the build

The third row is the risk. DITA treats unprofiled content as shared, which is right for a build and dangerous for an answer. A shared step that says --version=v2-alpha-tpuv6e appears in every build, and in Figure 3 it ranked third for a TPU7x question. audit_scope finds these: it looks for any value that belongs to one generation (a version string, a machine type, a key value) inside a chunk that is in scope for all of them. Each finding becomes an issue for the information architect. The writer fixes the profiling, and the next build reads the fix.

Figure 8
From map and topic to scope fields on each chunk
TPU7xv6eshared, no attributeshared text with a one-generation value
Each chunk stores one true or false field per generation in the subject scheme. Cascading decides most of them. The last row is in scope for everything, so the filter alone can't stop it. The audit catches it before any reader can.

5.3 Filter first, then search

Firestore vector search can combine a nearest-neighbour query with other filters, so the filter runs before the search. The filtered query needs a composite vector index12. VALID uses only equality filters on the scope fields, the pattern the Firestore documentation shows (where("in_tpu7x", "==", True)), with one composite index per generation. It doesn't depend on range or array filters inside a vector query, which the documentation doesn't describe.

Figure 9
Filter after the search compared with filter before it, for a TPU7x question
The left design is what most RAG stacks do when metadata is added late. The right design is the one rule VALID can't break: the scope filter is part of every query, and no code path removes it.

Exact terms matter in this content. Version strings, machine types such as tpu7x-standard-4t, and flags are rare tokens that dense vectors handle poorly. VALID also runs a BM25 search with SQLite FTS524 over the same scope, and merges the two lists with reciprocal rank fusion30. This is the hybrid retrieval pattern from QueryForge26, with the scope filter applied to both lists.

5.4 Agent tools

VALID has nine tools. Three run at index time and six at question time. One calls the model.

Index time · on every docs merge

1. Resolve profiles resolve_profiles

Parses the maps and topics with lxml. Applies map cascading, then element profiling, to give each chunk its scope. Chunks follow DITA structure: one section, one table or one group of steps. Fails the build on any value not in the subject scheme.

output: chunks with text, source path, line and one scope field per generation

2. Audit the scope audit_scope check

Finds shared chunks that contain a value owned by one generation: a version string, a machine type, or the resolved value of a generation key. Opens one issue per finding for the information architect.

output: scope findings with file and line; issues in GitHub

3. Embed and store embed_chunks

Embeds changed chunks with Gemini Embedding 2 at 1,536 dimensions, a recommended size under Firestore's 2,048 limit1214. Writes vectors and scope fields to Firestore, and text and scope to the BM25 index.

output: Firestore documents and FTS5 rows; only changed chunks are re-embedded
Question time · on every question

4. Decide the scope resolve_scope

Matches the question against the subject scheme: generation names, other names such as Trillium and Ironwood, accelerator types and machine types. No model call. Returns one generation, several, or none.

output: scope list and the words that matched

5. Search inside the scope retrieve_in_scope

Embeds the question, runs Firestore find_nearest with the scope pre-filter, runs BM25 with the same scope, and fuses the lists. For two generations, it runs once per generation and labels each list.

output: up to 5 chunks per generation, every one in scope, with scores

6. Write the answer generate_answer model

Calls Gemini 3.8 Flash with structured output. The schema requires a scope field and a citation on every step, and the citation must come from an enum of the retrieved chunk IDs, so Gemini can't cite anything it wasn't given. AlignR uses the same enum method for keys and sources29.

output: JSON answer with steps, citations and scope

7. Check the answer check_answer check

Three plain Python checks. Every citation is in scope. Every number, unit, flag, command and version string appears in its cited chunk. No value owned by an out-of-scope generation appears anywhere in the answer. The grounding check comes from KnowledgeFlow28.

output: pass, or the failed steps with reasons

8. Refuse or ask refuse_or_ask

No scope and a scope-dependent question: asks the reader to choose a generation. Scope but nothing in scope, or checks still failing: refuses, says what is missing, and opens a gap issue for the writer.

output: a choice for the reader, or a refusal and a gap issue

9. Log the question log_question

Writes one row per question to BigQuery: question, scope, chunk IDs and scopes, check results, outcome, tokens and cost.

output: rows in the question log

5.5 Agent loop

The model decides how to phrase the answer. The checks decide whether it can be sent. A failed step goes back to Gemini with its reason, up to two times, with the same in-scope chunks. VALID never widens the search to fix a failure.

Figure 10
Agent loop for one question
Three ways out, and only one is an answer. A question to the reader and a refusal are designed outcomes, as in VaultRAG25. Each refusal names the missing content, so it becomes work for a writer instead of a dead end.

5.8 What VALID keeps from VaultRAG

It runs on Cloud Run and Firestore Vector Search, refuses at five guardrail stages, and passed 17 of 20 queries in its own guardrail evaluation, with the three misses analysed25. VALID keeps its spine and replaces what was specific to plain text.

§7 Success Metrics

The MVP is measured on a trap set: questions whose correct answer differs between v5p, v6e and TPU7x. The set has 60 scoped questions: four facts (the three in Figure 2, plus supported frameworks) for each of three generations, in five wordings each. It also has 10 questions with no generation, and 10 that name two generations. Each question has a known answer and known source chunks. The same set runs against an unfiltered baseline built from the same chunks.
